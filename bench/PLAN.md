# Bench: какой поисковый провайдер под какой сценарий

**Цель:** прогнать всех провайдеров `wsearch` под разными сценариями использования,
получить матрицу «сценарий → лучший провайдер» и **рекомендации** (не внедрять сразу!)
по недетерминированному роутингу — чтобы агент понимал, когда какой тул поиска использовать.

Владелец явно попросил: **результат — отчёт и рекомендации**, изменения в тул/скилл —
отдельным решением после согласования.

## Этапы

### 1. Research: существующие бенчмарки (сабагенты, параллельно)
- [x] Изучить бенчмарки веб-поиска для агентов → `bench/research-benchmarks.md` ГОТОВ.
      Ключевые выводы: primary-метрика **hit@3 по gold URL/domain** (FRAMES-паттерн,
      объективна и различима на N=30), второй сигнал — **LLM-judge relevance@3**
      reference-free 0/1/2 (Tavily/Quotient: сильнее answer-only), freshness по
      published_date + judge «актуально ли». Урок Octen: один провайдер в разных
      tier'ах даёт разброс 20+ п.п. — фиксируем параметры. N=30 → выводы только
      по разницам >15 п.п. nDCG@10 не берём (стоимость разметки не окупается).
- [ ] Собрать реальные сценарии из истории моих сессий (`~/.claude/projects/*.jsonl`):
      какие запросы я реально делал (RU/EN, свежесть, семантика, факты, код).
      Выход: `bench/research-user-history.md`.

### 2. Датасет сценариев
- [ ] `bench/dataset.jsonl` — 5–7 сценариев × 4–6 запросов (~25–35 запросов):
      - `ru-general` — русскоязычный общий поиск
      - `ru-news` — RU-свежесть (новости, `--freshness`)
      - `en-news` — EN-свежесть
      - `exact-fact` — точный факт / длинный хвост
      - `semantic` — «по смыслу», исследовательский запрос
      - `code-docs` — код, документация, версии библиотек
      - `local-ru` — локальная специфика (регион, цены, организации РФ)
- Оси оценки: релевантность топ-N (hit@k), свежесть дат, RU-поклон, качество сниппетов,
  латентность, стабильность.

### 3. Раннер
- [ ] `bench/run_bench.py` — python3 stdlib: читает dataset.jsonl, вызывает
      `wsearch search --provider X --json` по очереди (sequential, щадяще),
      пишет `bench/results/<scenario>__<provider>.json`.
- Кого прогоняем: tavily, youcom, exa, brave, linkup, parallel-anon, ddg.
- Кого НЕ прогоняем: `zai` (исчерпан до 18.09 — локальный счётчик всё равно скипает),
  `parallel` keyed ($-грант — не тратить на бенчмарк; parallel-anon его заменяет).

### 4. Оценка
- [ ] Ручная разметка релевантности топ-3 (LLM-оценка в основном контексте или сабагентом):
      2 = прямо в точку, 1 = по теме, 0 = мимо. Считаем hit@3, avg score, латентность.
- [ ] Свежесть: доля результатов с датой ≤ 7 дней для news-сценариев.

### 5. Отчёт
- [ ] `bench/REPORT.md`:
      - матрица «сценарий × провайдер» со скорами;
      - выводы: кто в чём лучше/хуже (RU, новости, семантика, факты, код);
      - **рекомендации** по роутингу по сценарию (варианты: intent-флаги в CLI,
        правила в SKILL.md, автоматический выбор);
      - что НЕ трогаем (политика квот остаётся: экономика ≠ качество — их надо
        совместить: качество внутри экономического эшелона).

## Бюджет квот на прогон
~7 провайдеров × ~30 запросов ≈ до 210 вызовов:
tavily ~30 (из 1000/мес — ок), youcom ~30 (из 100/день — ок), exa ~30 (из 1400 — ок),
brave ~30 (из 2000 — ок), linkup ~30 (из 4000 — ок), parallel-anon/ddg — бесплатно.
$-гранты (parallel keyed, youcom keyed) — НЕ ТРАТИМ.
